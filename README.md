# 标书检查 Lite（BidCheck-Lite）

面向福建省建设工程招投标的**投标文件符合性检查工具**。上传一份招标（磋商）文件和一份投标（响应）文件，几秒到一分钟内逐条给出"招标要求什么、投标写了什么、差在哪、在第几页"。

- 双击即用：解压 → 双击 `标书检查.exe` → 浏览器自动打开，不装 Python、不装数据库、不用登录。
- 确定性优先：绝大多数条目靠解析 PDF/Word 的结构（前附表、否决条款、表单清单、投标函、清单汇总表）直接比对，**不是把标书塞给大模型让它"看看"**。大模型只用于少数语义条目，且只看一小段原文，引用的原文必须能在投标文件里找到，否则降级为"待人工"。
- 每条结论都带定位：招标文件页码 + 章节/条款，投标文件页码 + 表单，鼠标停上去可看原文摘录。
- 两种福建模板自动识别：**房建市政标准施工招标文件（公共资源交易平台，评定分离）** 与 **政府采购竞争性磋商文件（工程类）**。
- Word 也行：招标、投标文件都支持 `.docx`（PDF 更准）。扫描件证书可选阿里云视觉模型 OCR。

> 本工具是从开源项目 [BidMaster-Pro](https://github.com/guangshu100/BidMaster-Pro) 的"标书检查"模块出发，**把检查内核整个重写**后独立出来的：原实现是把标书前几千字连同提示词交给大模型输出 JSON，对几十万字、上千页的标书基本等于凭空猜；这里改成先结构化解析再逐条核对。

## 快速开始

### 方式 A：直接用打包版（推荐给不写代码的同事）

1. 到 [Releases](../../releases) 下载 `标书检查Lite.zip`（约 100 MB），解压到任意目录。
2. 双击 `标书检查.exe`。没有黑窗口，几秒后浏览器自动打开 `http://127.0.0.1:8765/`。
3. 拖入两份文件，点「开始检查」。
4. 用完点右上角「退出程序」。数据都在 exe 旁边的 `lite_data/` 目录，删掉即恢复初始状态。

杀毒软件可能拦截打包程序，选"允许"即可。如果页面打不开，看 `lite_data/server.log`。

### 方式 B：源码运行

需要 Python 3.12。

```bat
git clone https://github.com/leafpaper/BidCheck-Lite.git
cd BidCheck-Lite
uv venv .venv --python 3.12          :: 或 python -m venv .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.txt
检查标书.bat                          :: 启动本地服务并打开浏览器
```

## 它检查什么

检查条目按招标文件的**否决/无效条款**组织，先查"会不会被废标"，再查"会不会丢分"。条目的来源是网上能查到的真实废标原因（全国统计榜单、福建各地中标候选人公示里的否决原因、财政部与福建省财政厅的无效响应规定）逐条对照引擎能力后补齐的，见 [docs/v0.2-废标覆盖方案.md](docs/v0.2-废标覆盖方案.md)。

判定方式标记：**文** = 解析 PDF/Word 文字层与表格直接比对，不花 token；**OCR** = 扫描件交给视觉模型读要素（需阿里云 key）；**LLM** = 只把一小段原文交给大模型判断；**人工** = 单份文件判不了，给出招标依据位置让你自查。

### 查不到的（单份文件判不了，只给自查提示）

- 串标特征：MAC 地址、IP、CA 归属、保证金转出账户与其他投标人相同、内部识别码相同。
- 需要联网查政府平台的项：信用综合评价得分、建筑市场黑名单、安全生产标准化 D 级、四库一平台业绩核验。
- 电子签章有没有盖：电子标以 CA 签章为准，PDF 文字层看不到。
- 低于成本价：没有可靠算法，评标也是先要求说明再判。
- 单价 85% 线：需要招标控制价清单或 XML。

### 每次检查花多少 token

- 确定性规则（上表标"文"的 50 多条）：0。
- OCR：施工标典型 20 页左右、上限 24 页，每页约 2k token；同一份文件第二次检查命中缓存不再花。
- 大模型：只有 4 条规则、上限 16 次调用，每次约 4.5k token；同一份文件同一片段的判定结果缓存，改标书重导出后才重新判。

## 结果怎么读

| 判定 | 含义 |
|---|---|
| **不通过** | 招标文件有明确要求且投标文件不满足或未找到。**否决级**条目不通过时整份报告风险等级为"高"。 |
| **警告** | 有疑点但不能机器定论：如偏离表只有表头、某承诺未检索到、人员文字层只识别到部分。 |
| **待人工** | 工具只能定位不能判断：扫描件未 OCR、需要现场核对的事项、超预算降级的条目。 |
| **通过** | 要求与响应都找到了并且一致。 |
| **不适用** | 本项目不涉及（如不接受联合体时的联合体协议）。 |

每条包含：招标要求原文与位置、投标实际内容与位置、缺什么、怎么改。报告可下载为 Markdown 或 JSON；JSON 里 `findings` 是完整结构化结果，`hard_values` 是抽出的招标硬值（控制价/工期/有效期/保证金/资质要求…）。

## 设置：OCR 与大模型

右上角「⚙ 设置」。key 只保存在本机 `lite_data/settings.json`。

| 项 | 用途 | 不填会怎样 |
|---|---|---|
| 阿里云百炼 key | 视觉模型 `qwen-vl-max` 读扫描件（执照、资质证、安许证、建造师证、安 B/C 证、保证金回单） | 相关条目标为"待人工"，其余不受影响 |
| LLM key + 接口地址 + 模型名 | OpenAI 兼容接口。默认 DeepSeek，点「获取可用模型」自动列出（当前为 `deepseek-flash` / `deepseek-v4-pro`） | 需要语义判断的条目标为"待人工"（目前只有施工标模板有这类条目，磋商模板全部是确定性规则） |

费用控制：OCR 每次检查默认最多 20 页，只扫证书所在页，结果按文件哈希缓存；LLM 每条规则最多 2 次调用，只喂 ≤ 4000 字的证据窗口，`temperature 0.1`。一对上千页的标书，首跑通常 OCR 十几页、LLM 十几次，第二次跑全部命中缓存。

## 工作原理

```
招标文件 ──► 解析(PyMuPDF 文本 + pdfplumber 表格/或 docx) ──► 模板识别 ──► 抽取要求
                                                                     │  前附表 / 否决条款 / 数据表 / 人员配备
                                                                     │  表单清单 / 附录参数 / 硬值
投标文件 ──► 解析 ──► 建立索引（节与表单页范围、扫描页归属、投标函数值、清单汇总、人员表、技术段）
                                                                     ▼
                                    规则引擎：确定性规则 ──► 汇总 OCR 需求页一次识别 ──► LLM 窗口判断
                                                                     ▼
                                              报告：Finding[] + 摘要 + 风险等级 + Markdown/JSON
```

几个关键设计：

- **文本以 PyMuPDF 为准，表格只在需要的页用 pdfplumber**。pdfplumber 的加粗双写伪影（"条条款款"）、竖排单字、康熙部首兼容字、全角数字、中文大写金额都在 `textnorm.py` 统一归一。
- **章节靠标题正则 + 目录页排除，不靠页码**。目录页（同页出现 ≥ 5 个章标题）不作锚点；Word 文件会先合成"页"（表格后、附件标题前分页，目录行合并成目录页），让同一套页式解析器可用。
- **规则只依赖模型对象**（`TenderRequirements`、`BidIndex`），不碰 PDF。每条规则声明 `severity`（否决级/主要/次要）与 `method`（规则/表格/LLM/OCR/人工），按模板过滤装载。
- **LLM 的引用必须是窗口原文子串**，否则该条降级为"待人工"——这是防幻觉的硬约束。
- **缓存**：解析结果、表格、OCR 文本按文件 SHA-256 缓存在 `lite_data/cache`，跨次运行复用。

.venv\Scripts\python.exe -m services.fujian_check.cli check ^

`parse-tender` 单独就有用：它输出前附表硬值、否决条款清单、表单清单，相当于一份招标文件解读。

环境变量（可替代页面设置）：`ALIYUN_API_KEY`、`FJ_LLM_API_KEY`、`FJ_LLM_API_BASE`、`FJ_LLM_MODEL`、`FJ_LITE_PORT`（默认 8765，被占用时自动向后找）、`FJ_LITE_DATA`（数据目录）、`FJ_CACHE_DIR`。

也可以作为库调用：

```python
import asyncio
from services.fujian_check.engine import run_check
report = asyncio.run(run_check("招标.pdf", "投标.pdf", llm=None, use_llm=False, use_ocr=False))
print(report.risk_level, report.summary)
for f in report.findings:
    if f.verdict == "fail":
        print(f.rule_id, f.requirement, "→", f.actual, [e.page for e in f.evidence])
```

## 已知边界

- 只验证了上述两种福建模板；其他省份/平台、九部委通用版、水利等专业模板会被识别为"未知模板"，只跑通用交叉一致性条目，置信度很低。
- 单价 85% 线（详细评审 7.1.1/7.1.2/7.1.4/7.1.6）需要招标控制价清单或 XML，目前标为待人工。
- 签署日期只能读文字层：福州平台生成的表单落款日期在文字层，手工扫描的承诺函日期在图片里读不到（授权委托书、身份证、社保、保函走 OCR）。
- 社保、授权委托书、保函三类 OCR 判定依赖视觉模型对手写/盖章件的识别质量，结论标「OCR」且置信度 0.6–0.75，请以人工复核为准。
- 定标文件只查表单齐全与项目负责人一致，不做 100 分评分模拟。
- 雷同性、CA 归属、XML 软硬件信息在 PDF 上无法判定，输出自查提示。
- Word 支持基于合成样本验证，真实 Word 标书的表格/标题样式可能不同，首次使用请与 PDF 结果对照。
- 打包版只做了 Windows 10/11 x64。

## 目录结构

```
services/fujian_check/
├── engine.py            run_check 编排 + 进度回调
├── models.py            全部数据模型（Location / Finding / TenderRequirements / BidIndex / CheckReport …）
├── pdf_reader.py        PyMuPDF 逐页文本 + pdfplumber 指定页表格；页脚剥离；扫描页/目录页判定
├── docx_reader.py       Word → 合成页（含目录页识别）
├── textnorm.py          全角/双写/竖排/康熙部首/中文金额归一
├── cache.py             解析 / 表格 / OCR 磁盘缓存
├── profiles/            模板定义与自动识别（fujian_platform / fujian_gov_cs / jiubuwei stub）
├── tender/              招标文件抽取：章节、前附表、否决条款、数据表、表单清单、附录、磋商文件专用 gov_cs
├── bid/                 投标文件索引：节/表单范围、投标函、人员表、技术段、响应文件专用 gov_cs
├── rules/               规则组 group_*.py（PROFILES 属性控制装载）+ retrieval / llm_judge / ocr
├── report.py            汇总、风险等级、Markdown、平台兼容 JSON
├── cli.py               命令行
├── lite/                单页小程序：server.py（FastAPI）+ index.html + build.spec
└── tests/               单测 + 黄金样本断言
```
